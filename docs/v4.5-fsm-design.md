# v4.5 — FSM platform + settings-as-context (design)

Spine doc for roadmap bugs **N** (central FSM platform) and **O** (settings are
FSM context). Engine lives in core; **every machine is declared in YAML by the
plugin that owns it**. The interface is kept thin so the engine can later be
replaced by a cns-based implementation (ref: github.com/fruwe/cns_statemachine).

> **Status (v4.5):** Eve tracks **Determa State 0.2.x**
> ([spec](https://github.com/fruwehq/determa-state-spec) and
> [Python reference implementation](https://github.com/fruwehq/determa-state-python)).
> The original `state_machine:`/`transitions:` sketch below is superseded by
> Determa's format-1 bundles; see **"Reconciliation with Determa State"** below.
> The Eve↔Determa seam is `eve_sdk/fsm.py` (`EveFsm`).

## Why

Today state is scattered (`eve_sdk/state.py` enums, `state_machine.py` derivation,
`desired_state_for`/`provider_state_for`/`record_*` across dispatch) and **config
lives outside it entirely**. So `providers-status` could resolve config one way
and dispatch another — Vultr ✗ while creatable, AWS "configured" off ambient
`~/.aws`. The cure: one engine that owns both **state** and **context (settings)**
and hands them to every command identically. If config is always read from the
machine's context, status and dispatch *physically cannot* diverge.

## Core model

- **Machine definition** — declarative YAML a plugin ships. Describes one *kind*
  of machine (a provider, a package, …): its states, transitions, and the shape
  of its context (variables + settings).
- **Machine instance** — a live entity the engine tracks: `(definition, key,
  current_state, context)`. Keys: a provider id; an instance name; an
  `(instance, package)` pair; etc.
- **Context** — the machine's state variables, including **resolved settings**.
  The single source commands read config from.
- **Event** — a verb that may cause a transition. Events are the existing CLI
  verbs (`configure`, `up`, `down`, `provision`, `install`, `probe`, …).
- **Transition** — `from --on(event)--> to`, optionally gated by a **guard** over
  context, effected by an **action** (a plugin command). Action succeeds → land
  in `to`; fails → an error state.
- **Observe/reconcile** — a read-only command maps real-world status back into a
  state (e.g. connectivity → `reachable`, terraform status → `running`). Keeps
  the machine honest about drift.
- **Storage** — per machine kind: `host` (persisted state record) or `client`
  (derived live, not persisted). The engine owns persistence; machines don't.

## Plugin-declared YAML (the schema)

A `state_machine:` block in `eve-plugin.yaml` (or a referenced `fsm.yaml`):

```yaml
state_machine:
  scope: provider                 # provider | instance | package | os | bundle
  initial: unconfigured
  storage: host                   # host | client

  # Context = state variables. `setting`-sourced vars are resolved by the engine
  # (default -> global override -> per-instance override) and exposed to every
  # command of this machine via env_var. `null` default == the explicit "unset".
  context:
    api_key:
      source: secret              # setting | secret | observed | derived
      type: secret
      default: null               # unset
      scope: global               # global | instance | both
      env_var: VULTR_API_KEY
    region:
      source: setting
      type: string
      default: ""
      scope: both
      env_var: VULTR_REGION

  states:
    unconfigured: {}
    configured: {}
    reachable: {}

  transitions:
    - { from: "*",          on: resolve, to: configured,   guard: "api_key != null" }
    - { from: configured,   on: probe,   to: reachable,    action: {command: connectivity}, guard_on_result: "reachable == 'yes'" }
    - { from: "*",          on: resolve, to: unconfigured, guard: "api_key == null" }

  observe:                        # read-only reconciliation
    command: connectivity         # emits {configured, reachable, notes}
    maps: { reachable: reachable, configured: configured }
```

Notes:
- **Guards** are simple expressions over context (no arbitrary code); a small,
  safe evaluator. Result-guards (`guard_on_result`) check an action's JSON output.
- **Actions/commands** are the plugin's existing `commands:` — the FSM references
  them by name, it doesn't introduce a second command surface.
- A package machine looks the same with `scope: package`, states
  `{missing, installing, installed, failed, removed}`, events
  `{install, status, down}`, and context for its settings.

## Repository split (generic engine vs eve adapters)

The engine is its **own repository** — a generic, eve-agnostic FSM library; eve
depends on it one-way (like every other agnostic-core boundary). This makes the
"swap for a cns-based engine later" goal enforceable: the repo is the swappable
unit with a published interface, not a module that can drift into eve internals.

| Lives in the **engine repo** (generic) | Lives in **eve** (adapters) |
|---|---|
| Parse/validate a machine definition (YAML) | The `state_machine:` YAML in each plugin |
| Hold `(state, context)`; evaluate guards; fire transitions | Resolve settings → context (default→global→instance); inject secrets |
| Determine valid events; expose current state | Map eve commands ↔ FSM actions; entity→machine wiring |
| **Interfaces** for storage, action execution, context provider | **Implement** those interfaces (Workdir storage, run plugin command, ConfigEnv/Secrets) |

The engine never imports eve and never names a provider/package/OS — it just runs
whatever machine YAML + callbacks it is handed.

## The platform interface (the engine↔eve boundary)

Thin, storage- and engine-agnostic — this *is* the repo boundary and the cns seam:

```python
class Machine:                    # one definition + key
    state: str
    context: Mapping[str, str]    # resolved settings + observed vars

class FSM:
    def load(kind, plugin) -> Definition          # parse + validate YAML
    def machine(scope, key, *, registry=None) -> Machine
    def context(scope, key) -> Mapping[str, str]  # resolved settings (THE helper M/O need)
    def fire(scope, key, event, *, extra_args=()) -> Result   # run transition (guard->action->persist)
    def observe(scope, key) -> Machine            # reconcile from the observe command
    def states(scope, key) -> StateView           # current state + available events (for TUI/CLI)
```

`context()` is the one shared resolver from bug M: `providers-status`, dispatch,
and connectivity all call it, so they cannot see different config/secrets.

## Settings-as-context (the bug-killer)

Resolution order, done once by the engine: **plugin default → global override
(`~/.config/eve/config.yaml` / `eve settings ...` / TUI) → per-instance override
(instance entry / `eve instance settings ...` / TUI)**. The resolved value is put
into context and exposed to every command of that machine via `env_var`. There is
no other path to config — no plugin reads `~/.aws` or ambient env behind eve's
back; if a provider needs ambient creds, it declares them as a `setting` eve
resolves and injects.

## Mapping current eve → machines

| Machine (scope) | States (today → YAML) | Owner plugin |
|---|---|---|
| provider | unconfigured/configured/reachable (new; was the secret-less probe) | provider |
| instance | absent/creating/running/stopped/error (`PROVIDER_STATES`) + desired | provider |
| provision | unknown/provisioning/provisioned/error (`PROVISION_STATES`) | provider (os bootstrap) |
| package | missing/installing/installed/failed/removed (`PACKAGE_STATES`) | package |
| os | (image/bootstrap readiness) | os |
| bundle | derived from member packages | bundle |

`state.py`'s hardcoded enums move into the owning plugins' YAML; `state_machine.py`
+ the `*_state_for`/`record_*` functions collapse into `FSM`. `Engine`/`Workdir`
keep persistence, but behind `FSM`'s storage seam.

## Storage (host vs client)

- **host** — durable per-entity state record (instances, provision, packages).
  Lives under `~/.local/state/eve/` (roadmap P).
- **client** — derived live, not persisted (provider configured/reachable is
  recomputed via `observe`; cached briefly only).

## Open decisions (need your call)

1. **Instance lifecycle ownership** — does the *provider* plugin declare the
   instance FSM (lifecycles differ: vultr vs docker vs local-qemu), or is there a
   shared core instance FSM with provider-supplied transition actions? I lean
   **provider-declared** for honesty; it's more YAML per provider.
2. **Guard expression language** — minimal safe DSL (`==`, `!=`, `&&`, presence)
   vs. something richer. I lean **minimal**.
3. **Bundle/OS machines** — model now, or stub their states until B/§14 settle?
   I lean **stub** (define scope, minimal states) to keep N/O focused.
4. **One YAML block vs separate `fsm.yaml`** — inline in `eve-plugin.yaml` keeps
   it together; a separate file keeps manifests small. I lean **inline** with an
   optional `$ref`. (Orthogonal to the engine repo split — plugins declare their
   machine YAML in eve either way; the engine just parses it.)
5. **Engine repo home + name** — a generic FSM library, eve-agnostic. Under the
   eve org (`fruwehq/…`) or your personal org alongside cns (`fruwe/…`)? Generic
   name (`statemachine`, a modern cns) vs eve-scoped (`eve-fsm`)? I lean a
   **generic name** since the whole point is reuse + a future cns-based swap, but
   it's your call where it lives.

## Reconciliation with Determa State (as built)

The engine is real now, so this supersedes the speculative `state_machine:` schema
above. (History: the engine started as **harel**, was renamed **determa-state**, and
at spec **v0.1.0** pivoted to *format-1 bundles* + a *pure-functional interface*.
Eve now tracks the compatible 0.2.x line.)

- **Machines are format-1 bundles.** A plugin ships a Determa State bundle: `format: 1`,
  a `namespace`, shared `events` (host-delivered events are `direction: input`), and
  `machines: [{machine_id, root}]`. States are `states:` under `root:`; transitions are
  `on_events: { <event>: { transition_to, guard, action } }`; the machine's config lives
  in `variables:` (root-declared, `external: true` for eve-resolved values). Guards are
  **CEL**; actions are the structured set (`assign`/`send`/`refresh`/`spawn`/`cancel`/
  `stop`). Format 1 has **no orthogonal regions** — independent lifecycles are separate
  machines in one bundle (which matches eve's persistence: `provider_state` and
  `provision_state` are separate fields anyway).
- **Settings are `external` variables.** eve resolves a machine's declared `external`
  variables (settings + secrets) via one shared resolver and seeds them as **creation
  bindings**. A settings change is delivered as the reserved **`env` event**; the
  machine's `env` handler adopts it via **`refresh`**. One context ⇒ status and dispatch
  cannot diverge.
- **Side effects are host-driven.** Engine actions are sandboxed (no host calls), so eve
  runs the real command (connectivity probe, terraform, provision) and delivers the
  outcome back as an event (`probe_ok`/`probe_fail`). `configured` is a guarded
  transition on the secret; `reachable` is a substate of `configured` reached by the
  probe result.
- **The interface is pure-functional (spec §8).** `create(bundle, machine_id, id,
  creation_id, bindings)` and `dispatch(bundle, prior_state, delivery)` map a plain
  aggregate-state dict to the next one — no engine-held mutable objects. This fits eve
  exactly: seed from persisted state, fire one event, persist the result.
- **The platform** is `eve_sdk/fsm.py` — `EveFsm` holds loaded bundles + live aggregate
  states and takes a pluggable `ContextResolver`
  (`(scope, key, external_names) -> {name: value}`), the seam where the single
  ConfigEnv+secrets resolver plugs in. Surface: `load` / `aggregate` / `fire` /
  `refresh` / `leaves` / `state` / `context` / `view`. `import determa.state` appears
  only in this module — nothing else in eve names the engine.

### Landed / next
- ☑ **Increment 1** — `EveFsm` + a synthetic provider machine
  (`tests/fsm_fixtures/provider.yaml`) + `tests/test_fsm_platform.py` proving
  configured/reachable are FSM-computed from injected context and re-derive on a settings
  change. Determa State is a required project dependency; the FSM tests do not skip.
- ☑ **Real resolver** — `provider_context_resolver()` in `eve_sdk/fsm.py`: resolves each
  declared external variable (named as its eve env var) through
  `resolved_provider_environment()`, the same builder used by dispatch and connectivity.
  Required fields are read from the manifest's actual `config_schema.config` and
  `config_schema.secrets` blocks. Provider and package commands receive operation-local
  environments: explicit process transport/routing variables, core configuration, and
  only that target plugin's declared config and secrets. Ambient or sibling-plugin
  credentials cannot cross the command boundary.
- ☑ **Core provider machine** — `core/fsm/provider.yaml`: one shared provider lifecycle
  (unconfigured → configured → reachable) for *every* provider. `is_configured` is
  derived by `provider_configured_resolver()` from the plugin's `config_schema`
  universally `required` secrets/config fields plus the optional provider-only
  `required_any` alternative groups (via the shared path), so "configured" is
  eve-resolved, not a plugin's ambient self-report. The lifecycle is identical across
  providers, so it lives in `core/`, not per-provider. Tested end-to-end.

- ☑ **Rewire `providers-status`** — `configured` is now FSM-derived (`core/fsm/provider.yaml`
  + `provider_configured_resolver`); the `connectivity` command runs **only for
  `reachable`** (its self-reported `configured` is ignored) and only when configured.

- ◐ **Retire `state.py`/`state_machine.py` (live)** — decision: **adopt the cleaner
  vocabulary**; instead of a runtime migration, **delete all persisted state once** (no
  important instances) and start fresh on the machine vocabulary.
  - ☑ Machine vocabulary aligned (provider `unknown` initial + drift `observe_*` edges).
  - ☑ Clean slate: existing instances destroyed + deleted, per-instance state wiped, and
    `eve_sdk/fsm_migrate.py` retired (no migration needed).
  - ☑ **Vocabulary alignment:** `dispatch.provider_state_for` and the package state map
    write the machine vocabulary (`creating/starting/stopping/destroying`, `init`/`plan`→
    `creating`, package `reinstall`→`installed`); `state.py`'s state sets, the

    `valid-pending` fixture, and `test-plugins` all follow. Full suite green.
  - ☑ **FSM-driven status (write path):** `provider_state` is no longer a hand-maintained
    lookup table. `eve_sdk/instance_fsm.py` is the single lifecycle authority: dispatch
    maps a `(command, op_status)` to a machine event (`dispatch_event`) and
    `State.record_operation(provider_event=…)` **fires it into `core/fsm/instance.yaml`**
    seeded from the persisted `provider_state`, atomically inside the state write; the
    resulting leaf *is* the new `provider_state`. So the state a status read sees is
    exactly what the machine produced — the transition table and the machine cannot
    diverge because there is only the machine. `provider_state_for` is deleted;
    `provider_command.py` + `scripts/provider-dispatch` fire events. Live-validated on a
    real local-qemu instance (create→running, stop→stopped, start→running, destroy→absent,
    failure→error) + `scripts/test-lifecycle` green + a new `test_state.py` case.
  - ☑ **FSM-driven package state:** install, reinstall, removal, live status, interrupted
    operation recovery, and full-provision observations all fire events into
    `core/fsm/package.yaml`. Root-level observation transitions let authoritative probes
    reconcile an interrupted `installing` or `removing` state.
    - *Machine change:* every concrete provider state now accepts every operator command
      (routing to its transient), so a command's terminal outcome holds from any state
      (start recovers `absent`→`running`) — the provider command, not the machine, decides
      feasibility (a `start` that can't apply fails → `error`, it never silently no-ops).

  - **Remaining (read-path derivations):** `state_machine.py`'s `effective_provider_state`
    (the error→running display recovery), `should_apply_live_provider_state` (live-overlay

    machine), so no divergence risk remains. They stay as a thin status-render adapter.
  - ☑ **FSM-driven provision state:** `State.record_operation` maps provision operation
    statuses to `provision`/`provision_ok`/`provision_fail` and fires them through the

  rejected, so the shared command block is spelled out), `EveFsm` rewritten over
  `create`/`dispatch` (aggregates held per `(scope, key)`), `instance_fsm` seeds each
  provider leaf once by replaying a short event prefix and dispatches against the
  cached aggregate (dispatch is pure, the cache stays valid). The harel fallback import

- ☑ **Engine 0.2.0 upgrade** — 0.2.0 preserves the format-1 grammar and pure
  `load_bundle`/`create`/`dispatch` contract used by Eve. Its optional `ExecutionHost`
  and checkpoint stores are intentionally not adopted here: Eve already commits its
  operation metadata and lifecycle fields atomically in one locked state document.
  Seed-by-replay remains limited to the current context-free lifecycle graphs; future
  stateful machines must persist and restore full aggregates.
